# Capture rules

Capture only meaningful failures, rejected hypotheses, confirmed root causes, architecture or scope changes, user/technical decisions, deployment facts, security choices, and validation milestones. A content opportunity may be a short tag or asset record. Skip commands, routine edits, normal tests, package installs, chat transcripts, and private reasoning. Keep entries short and continue implementation.

Append corrections rather than rewriting wrong turns. Label observation, hypothesis, evidence, result, and validation separately. Never turn a hypothesis into a root cause without supporting evidence. For mid-project activation, create a `pre_pipeline_summary` event from visible sources and explicitly state what is unknown.
